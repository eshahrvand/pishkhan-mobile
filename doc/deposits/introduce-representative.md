# Introduce a new representative

Route: `/deposits/introduce-representative`. The deposit-list Representative
action and dashboard `deposit-representation-settings` service open this flow.
An optional entry deposit number is resolved against the fetched open deposits
in Cubit, including Persian digits and presentation separators.

## Behavior

- The initial form explicitly selects a deposit and permitted operation, then
  accepts a representative's national code and validity date. The currently
  approved operation is cheque-book issuance only.
- Until the calendar widget is supplied, dates are entered manually as Jalali
  `YYYY/MM/DD`. Input accepts Persian/Arabic digits, rejects impossible dates
  and dates before today, and stores the corresponding Gregorian UTC date.
- National codes use the existing checksum validator. Format validation is not
  an identity enquiry; cards therefore show the localized “New representative”
  title rather than an invented or verified person's name.
- Preliminary Save appends only to the immutable pending list in State. The
  screen switches from `RepresentativeInitialForm` to `RepresentativeList`.
- Add Another opens `RepresentativeSheet`, borrowing the same Cubit with
  `BlocProvider.value`. Save appends a draft; Cancel, swipe and system Back close
  the sheet without appending. Opening it again starts an empty form.
- Removing the last pending item restores the initial form. Final submission
  requires at least one pending item and terms acceptance. The terms link uses
  the existing unavailable-content feedback until approved terms are supplied.
- Pending submission locks list/terms edits through UI availability. Back and
  assistant navigation remain available and confirm discarding local changes.
- A failed submission preserves the list. Retry sends the same list and key;
  uncommitted edits and terms toggles do not change request identity. A changed
  submitted list gets a new key. Successful submission is non-resubmittable;
  receipt dismissal returns home.

## Implementation boundaries

`IntroduceRepresentativeScreen` directly creates `RepresentativeCubit` and
calls `fetchDeposits`. GetIt contains only actual repository dependencies.
The existing `LoadDeposits` boundary loads the deposit catalog; the new
`SubmitRepresentatives` boundary catches unexpected repository exceptions.
State is a plain Freezed `initial` factory/part-of file with independent catalog
and submission outcomes. Field actions validate only their own input and combine
stored validation results. Forms and list/footer sections subscribe locally.

The repository is **mock only**. `MockRepresentativeRepository` keeps request
identity/receipts in memory and returns a clearly labeled demo receipt. It
creates no banking authority and performs no identity enquiry or API call.
A future real adapter must send the prepared key and request data to the server;
server authorization, identity enquiry and durable idempotency remain necessary
at that boundary.

The existing representative card supports an optional status, custom action
icon and body/label colors. Existing callers retain their previous defaults.
Selects, text fields, buttons, checkbox, top bar, sheet header, assistant and exit
dialog reuse current components and SVGs. Figma's generated reference incorrectly
points the Back slot at a menu SVG despite rendering a chevron in both screenshots
(the full frame and the isolated navigation button). The existing Back chevron
matches the actual visual target; the mismatched menu asset is not used.
