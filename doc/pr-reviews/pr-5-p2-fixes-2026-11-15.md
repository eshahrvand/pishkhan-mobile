## مالکیت درخواست و جریان Back کیف پول

۱۳ مالک عملیات داده در کیف پول باقی مانده‌اند؛ درخواست تازه یا lifecycle تکراری به Cubitها اضافه نشده است:

| Cubit | مالکان عملیات | وضعیت‌هایی که Back را می‌بندند |
| --- | --- | --- |
| Overview | `fetchWallet` | `walletStatus` |
| Charge | `fetchWallet`, `requestOtp`, `submitPayment` | wallet / OTP / submission / share |
| Withdraw | `fetchWallet`, `requestOtp`, `submitPayment` | wallet / OTP / submission / share |
| Transfer | `fetchWallet`, `inquireRecipient`, `submitTransfer` | wallet / recipient / submission / share |
| Linked deposit | `fetchCatalog`, `submitChange` | catalog / submission |
| Transactions | `fetchTransactions` | transactions |

تمام موارد جدول زمانی gate می‌شوند که مقدار status برابر `loading` باشد. Share یک اثر پلتفرمی مستقل است و در جمع ۱۳ عملیات داده حساب نشده است.

مسیر خروج فرم:

```text
System Back / Header Back
        |
        +-- owning request loading --> UI blocks action
        |
        v
Cubit.requestBack()
        |
        +-- editable form with input --> confirmExit
        |                                  |
        |                         UI consumes command
        |                         and shows FlowExitSheet
        |                                  |
        |                         raw bool? result to Cubit
        |                                  |
        |                    true --> back; false/null --> stay
        |
        +-- empty/read-only page --> back
        |
        +-- completed payment/transfer receipt --> home
```

برای `back`، ابتدا PopScope با فرمان خروج مجاز بازسازی می‌شود و سپس listener در post-frame، pop را اجرا می‌کند؛ pop دوباره به scope بسته فرستاده نمی‌شود. برای Back/Close رسید شارژ، برداشت و انتقال، `go` به Dashboard Home انجام می‌شود تا فرم موفق دوباره در stack باز نشود. تغییر سپرده رسید ندارد: موفقیت، فرمان بازگشت به caller را منتشر می‌کند و اعلان موفقیت جداگانه اجرا می‌شود.

FlowNavigation یک دادهٔ State است؛ State منطق دستی، getter یا ساختار جدیدی خارج از Freezed ندارد. پاک‌شدن navigation هنگام مصرف فرمان modal، نیاز واقعی consumer است. failure/message و داده‌های فرم در Stay/dismissal پاک نمی‌شوند.

## پیگیری بازبینی 17c9c7b — تداخل debounce و تأیید خروج

بازبین یک تداخل زمانی باقی‌مانده را گزارش کرد: ورود مقصد معتبر، Back پیش از ۳۵۰ms، شروع استعلام پشت شیت تأیید خروج و سپس خروج با درخواست معلق. بسته‌بودن Back صفحه، دکمهٔ خروج شیتِ ازقبل‌باز را پوشش نمی‌داد.

اصلاح در مالک جریان انجام شد:

- `requestBack` پیش از انتشار فرمان، timer زمان‌بندی‌شدهٔ استعلام را لغو می‌کند؛ در زمان بازبودن شیت، درخواست جدیدی از debounce شروع نمی‌شود.
- نتیجهٔ true فقط خروج مجاز را منتشر می‌کند. نتیجهٔ false/null، فقط برای مقصد معتبر با `recipientStatus.initial` به همان `inquireRecipient` موجود تفویض می‌شود؛ نتیجهٔ موفق/ناموفق قبلی دوباره استعلام نمی‌شود.
- `isDestinationValid` همراه با ویرایش مقصد و همان یک بار اعتبارسنجی ذخیره می‌شود؛ نتیجهٔ modal اعتبارسنجی را تکرار نمی‌کند.
- Listener فقط نتیجهٔ خام را به action می‌دهد و آن را await می‌کند؛ زمان‌بندی و تصمیم شروع استعلام در UI قرار نگرفته است. هیچ loading/lifetime guard در Cubit اضافه نشده است.

شاهد تفکیک‌کننده: شش سناریوی واقعی UI برای Back سیستم/header و تصمیم خروج/ماندن/dismissal، **پیش از اصلاح هر شش مورد شکست خوردند**؛ انتظار صفر استعلام پشت شیت بود و یک استعلام شروع می‌شد. پس از اصلاح، همان سناریوها عبور کردند. در Stay/dismissal، تنها یک استعلام پس از بسته‌شدن شیت شروع می‌شود؛ تا پایان پاسخ، Back بسته و route زنده می‌ماند و پس از پاسخ، فرم با ورودی حفظ‌شده قابل ادامه است.

سه تست Cubit نیز عدم استعلام مقصد نامعتبر و عدم تکرار نتیجهٔ موفق/ناموفق قبلی را، با حفظ پیام خطای ثبت‌شده، بررسی می‌کنند.
