# Backend Meeting: Page Builder و Drawer

**وضعیت:** پیش‌نویس برای توافق API؛ هنوز قرارداد بانک نیست  
**مخاطب:** تیم Backend، تیم اپلیکیشن و مالک محصول  
**هدف جلسه:** توافق روی داده‌ای که صفحهٔ خانه و Drawer را می‌سازد؛ بدون سپردن اجرای کد یا کنترل آزاد مسیرهای اپ به سرور

در این سند، «Page Builder» سازوکار تعیین چیدمان صفحهٔ خانه است، «Drawer» فهرست گروه‌های ناوبری است و «route» نشانی داخلی هر صفحه در اپ است. نام فنی فیلدها و شناسه‌ها با قلم کد آمده تا در قرارداد API قابل استفاده باشد.

## ۱. مبنای فعلی پروژه

- اپ چهار تب اصلی دارد: `dashboard`, `cards`, `deposits`, `loans` (`AppPrimaryTab`).
- سرویس‌های هر گروه و Drawer فعلاً عمدتاً از فهرست‌های ثابت داخل اپ ساخته می‌شوند.
- شناسه‌های فعلی مانند `deposit-statement`, `card-issue`, `loan-estimate` در `DashboardService` و `ServiceRegistry` به صفحه‌ها و مسیرهای داخل اپ نگاشت می‌شوند.
- routes در `GoRouter` و داخل اپ تعریف شده‌اند. ارسال مستقیم مسیر از Backend یکی از دو گزینهٔ این سند است؛ در صورت انتخاب، اپ فقط مسیرهای دقیقاً ثبت‌شده را می‌پذیرد.
- در نسخهٔ فعلی پروژه آیکن‌ها محلی‌اند و دریافت آیکن از اینترنت هنوز پیاده نشده است. پیشنهاد این سند برای نسخهٔ آینده فرض می‌کند نشانی همهٔ آیکن‌ها را سرویس تصویر در اختیار اپ می‌گذارد و اپ آن‌ها را با یک Image Cache Manager دریافت و cache می‌کند؛ بنابراین فیلد `iconKey` در این قرارداد لازم نیست.
- مدل فعلی Drawer گروه و زیرآیتم سرویس دارد؛ جستجو، انتخاب و باز/بسته‌شدن منو در اپ مدیریت می‌شود.

## ۲. پیشنهاد اصلی

وضعیت بخش قبل، توصیف معماری فعلی اپ است؛ قراردادهای JSON در ادامه پیشنهاد جلسه‌اند و به معنی پیاده‌سازی یا وجود API در حال حاضر نیستند. نمونهٔ پاسخ در این سند گزیده است و به‌تنهایی پاسخ کامل و قابل‌استفادهٔ API نیست.

### مسئولیت Backend و اپ

| موضوع | مسئولیت Backend | مسئولیت اپ |
|---|---|---|
| تب و بخش | انتخاب شناسه‌های مجاز و ترتیب/نمایش آن‌ها | شناختن تب‌ها و نوع بخش‌های پیاده‌سازی‌شده و ساخت UI آن‌ها |
| فهرست سرویس | انتخاب شناسه‌های سرویس، متن/تصویر و فعال‌بودن نمایشی | اعتبارسنجی شناسه و نمایش؛ نگاشت به قابلیت و مقصد ثبت‌شده |
| دادهٔ بانکی مشتری | هیچ دادهٔ حساس را از Page Builder ارسال نکند | از API و مخزن دادهٔ مربوط به کارت/سپرده/وام دریافت کند |
| مجوز و شرایط بانکی | در API عملیاتی دوباره بررسی کند | فقط ورودی لازم را از جریان کاربر بگیرد؛ نمایش آیتم مجوز محسوب نمی‌شود |
| مقصد کلیک | یکی از قراردادهای مقصد توافق‌شده را مشخص کند | فقط مقصد و پارامترهای شناخته‌شده را اجرا کند |
| تصویر | URL امن و مشخصات فایل را بدهد | میزبان/قالب/اندازه را اعتبارسنجی و از مدیر cache تصویر استفاده کند |

Page Builder یک پاسخ چیدمان است و جایگزین APIهای داده‌ای فیچرها نیست. برای مثال customer-cards نام منبعی است که اپ می‌شناسد، نه endpointی که Backend از پاسخ Page Builder به اپ دیکته می‌کند.

یک سرویس **فهرست و چیدمان خانه** با نسخهٔ مشخص ارائه شود. پاسخ آن ترتیب چهار تب، بخش‌های داخل هر تب، سرویس‌های هر بخش و چیدمان Drawer را بدهد. Drawer می‌تواند گروه‌بندی متفاوتی داشته باشد، اما برای عنوان، آیکن و مقصد سرویس به همان شناسهٔ سرویس در فهرست مشترک ارجاع دهد تا دو تعریف ناسازگار از یک سرویس ساخته نشود.

اگر مالک یا زمان انتشار Drawer واقعاً جدا باشد، می‌توان چیدمان آن را از مسیر دیگری گرفت؛ در آن صورت هم پاسخ باید فقط به `serviceId`های فهرست مشترک ارجاع دهد و اطلاعات سرویس یا مقصد آن را دوباره تعریف نکند.

### Page Builder دقیقاً چه چیزی را تعیین می‌کند؟

Page Builder پاسخی از سمت Backend است که ترتیب تب‌ها، ترتیب بخش‌های داخل هر تب، گروه‌بندی سرویس‌ها و جای نمایش آن‌ها را مشخص می‌کند. اپ فقط بخش‌هایی را نمایش می‌دهد که از قبل پیاده‌سازی و پشتیبانی کرده است؛ پاسخ API نمی‌تواند ویجت یا کد اجرایی تازه بسازد. اطلاعات حساب، کارت، سپرده و وام از سرویس‌های داده‌ای خودشان می‌آید؛ Page Builder فقط چیدمان و شناسهٔ منبع داده را تعیین می‌کند.

| تب | بخش‌های فعلی اپ که Page Builder می‌تواند مرتب کند | منبع داده |
|---|---|---|
| `dashboard` | خلاصهٔ کیف پول، بنر دستیار/رسو، سرویس‌های برگزیده و میانبرها | `homeData` و فهرست سرویس‌ها |
| `cards` | نمایش پیمایشی کارت‌ها، عملیات کارت، میانبرهای عملیاتی | کارت‌های کاربر و قابلیت‌های هر کارت |
| `deposits` | نمایش پیمایشی سپرده‌ها، عملیات سپرده، عملیات چک و دسترسی سریع | سپرده‌های کاربر و قابلیت‌های هر سپرده |
| `loans` | نمایش پیمایشی وام‌ها، عملیات وام و میانبرهای عملیاتی | وام‌ها و اطلاعات اقساط |

برای نمونه، `tabs[].sections[]` می‌تواند تعیین کند که در تب کارت‌ها ابتدا `cards-carousel`، سپس `card-operations` و بعد `card-quick-actions` نمایش داده شوند. برای بخش فهرست کارت‌ها، Backend نشانی دلخواه سرویس داده را نمی‌فرستد؛ فقط `dataSource` شناخته‌شده را انتخاب می‌کند و اپ آن را به منبع دادهٔ مجاز وصل می‌کند.

## ۳. نشانی پیشنهادی برای دریافت چیدمان

```http
GET /mobile/v1/apps/{appId}/home-catalog
    ?platform=android
    &versionName=5.4.0
    &buildNumber=50400
    &locale=fa-IR
    &channel=bazaar
If-None-Match: "home-2026-10-26-42"
```

درخواست را اپ می‌سازد. جدول زیر روشن می‌کند هر مقدار از کجا می‌آید و سرور با آن چه می‌کند:

| پارامتر | الزامی | فرستنده و معنا | رفتار سرور در نبودن یا نامعتبر بودن |
|---|---:|---|---|
| `appId` | بله | اپ شناسهٔ ثابت محصول را می‌فرستد؛ نمونه: `pishkhan-mobile`. این مقدار برای انتخاب تنظیمات و فهرست همان محصول است. | درخواست با خطای قراردادی رد شود؛ سرور نباید بی‌صدا فهرست محصول دیگری را برگرداند. |
| `platform` | بله | اپ مقدار `android` یا `ios` را می‌فرستد تا سرور بخش‌ها و مقصدهای قابل‌پشتیبانی همان سیستم‌عامل را انتخاب کند. | مقدار ناشناخته با خطای ورودی رد شود. |
| `versionName` | بله | اپ نسخهٔ قابل‌نمایش نصب‌شده را می‌فرستد؛ نمونه: `5.4.0`. این مقدار برای گزارش و توضیح سازگاری نسخه خواناست. | قالب نامعتبر با خطای ورودی رد شود یا فقط همراه با `buildNumber` بررسی شود؛ رفتار انتخاب‌شده باید مستند باشد. |
| `buildNumber` | بله | اپ شمارهٔ ساخت نصب‌شده را به‌صورت عدد می‌فرستد. سرور از آن می‌فهمد آیا نسخهٔ اپ بخش یا سرویس خاصی را می‌شناسد. | مقدار غیرعددی یا منفی رد شود. اگر قابلیت به ساخت جدیدتری نیاز دارد، آیتم ناسازگار حذف یا غیرفعال شود. |
| `locale` | بله | زبان فعلی رابط کاربر را می‌فرستد؛ نمونه: `fa-IR`. سرور از آن برای متن‌های پویا استفاده می‌کند. | زبان پشتیبانی‌نشده به زبان پیش‌فرض توافق‌شده برگردد؛ پاسخ نباید عنوان خالی بدهد. |
| `channel` | ترجیحاً | اپ منبع نصب را می‌فرستد؛ نمونه: `bazaar`, `myket`, `direct`. فقط زمانی لازم است که چیدمان بر اساس منبع نصب تفاوت داشته باشد. | مقدار ناشناخته به فهرست عمومی برگردد یا با خطای ورودی رد شود؛ تصمیم باید در قرارداد ثبت شود. |

`If-None-Match` سرآیند `HTTP` است، نه پارامتر `query`:

| سرآیند | الزامی | فرستنده و معنا | رفتار پاسخ |
|---|---:|---|---|
| `If-None-Match` | خیر | اپ شناسهٔ نسخهٔ ذخیره‌شدهٔ فهرست را می‌فرستد تا سرور بررسی کند آیا محتوا تغییر کرده است. | اگر تغییری نکرده، سرور `304 Not Modified` و بدنهٔ خالی بدهد؛ در غیر این صورت `200` همراه فهرست تازه و `ETag` جدید. |

اطلاعات کاربر، نقش و مجوزها در صورت نیاز از توکن احراز هویت خوانده شوند؛ شناسه‌های شخصی به نشانی درخواست اضافه نشوند. اگر پاسخ برای هر کاربر فرق می‌کند، سرور و اپ باید نسخهٔ ذخیره‌شده را از نشست‌های دیگر جدا نگه دارند تا اطلاعات یک کاربر به کاربر دیگر نرسد.

### معنی عددهای `order` و آیتم‌های نمونهٔ تب کارت‌ها

عددهای `10`, `20`, `30` شمارهٔ صفحه، شناسه یا درجهٔ اهمیت نیستند؛ فقط ترتیب نمایش را در همان فهرست مشخص می‌کنند. اپ آن‌ها را از کوچک به بزرگ مرتب می‌کند. برای نمونه، در نوار تب‌ها `dashboard` با مقدار 10 قبل از `cards` با مقدار 20 می‌آید. داخل تب کارت‌ها، `cards-carousel` با مقدار 10 قبل از `card-operations` با مقدار 20 و آن هم قبل از `card-quick-actions` با مقدار 30 نمایش داده می‌شود. فاصلهٔ بین عددها برای این است که بعداً بتوان موردی را بین دو مورد جا داد؛ مثلاً مقدار 15 را بین 10 و 20 قرار داد، بدون اینکه بقیه را شماره‌گذاری مجدد کنیم. اگر دو مورد هم‌عدد شوند، `id` ترتیب ثانویه را تعیین می‌کند.

هر مجموعهٔ هم‌سطح، ترتیب جداگانهٔ خودش را دارد: ترتیب تب‌ها با `tabs[].order`، ترتیب بخش‌ها با `sections[].order` و ترتیب گروه‌ها/زیرآیتم‌های منو با `drawer.items[].order` و `children[].order` تعیین می‌شود. عدد یک بخش با عدد بخش‌های تب دیگر مقایسه نمی‌شود.

| مورد در نمونهٔ تب کارت‌ها | معنا و رفتار مورد انتظار |
|---|---|
| `id: "cards"` | این صفحه همان تب کارت‌هاست؛ شناسه باید با یکی از تب‌های شناخته‌شدهٔ اپ برابر باشد. |
| `order: 20` در تب | کارت‌ها پس از تب `dashboard` با ترتیب 10 نمایش داده می‌شوند؛ این عدد فقط ترتیب نوار تب‌ها را تعیین می‌کند. |
| `visible: true` | تب کارت‌ها در نوار اصلی قابل مشاهده باشد. اگر `false` شود، پنهان‌کردن آن باید با تصمیم محصول و مسیرهای دسترسی جایگزین هماهنگ باشد. |
| `sections` | فهرست بخش‌های سازندهٔ همین تب؛ اپ هر بخش را با نوع نمایش پشتیبانی‌شده می‌سازد. |
| `id: "cards-carousel"` | شناسهٔ پایدار بخش نمایش کارت‌ها؛ برای عیب‌یابی و شناسایی بخش است و به‌تنهایی ظاهر آن را تعیین نمی‌کند. |
| `type: "cards-carousel"` | به اپ می‌گوید از نمایشگر ازپیش‌ساختهٔ «نمایش پیمایشی کارت‌ها» استفاده کند. سرور widget تازه تعریف نمی‌کند. |
| `order: 10` در `cards-carousel` | این بخش اولین بخش محتوایی تب کارت‌هاست. |
| `dataSource: "customer-cards"` | کلید منبع دادهٔ شناخته‌شده در اپ برای کارت‌های همین کاربر است. این مقدار URL یا نام endpoint نیست؛ اپ خودش داده را از repository کارت می‌گیرد. |
| `id: "card-operations"` | شناسهٔ پایدار بخش عملیات معمول کارت‌ها. |
| `type: "service-grid"` | نمایش سرویس‌های این بخش به‌شکل شبکه‌ای استاندارد اپ. |
| `titleKey: "cards.operations"` | کلید عنوان بخش؛ اپ آن را به متن محلی‌سازی‌شدهٔ «عملیات کارت» وصل می‌کند. |
| `order: 20` در `card-operations` | این بخش پس از نمایشگر کارت‌ها قرار می‌گیرد. |
| `serviceIds: ["card-issue", "card-password", "card-virtual"]` | سه سرویس این شبکه به همین ترتیب می‌آیند. هر شناسه باید در `services[].id` تعریف شده باشد؛ عنوان، آیکن و مقصد از همان تعریف خوانده می‌شود. |
| `id: "card-quick-actions"` | شناسهٔ پایدار بخش میانبرهای کارت. |
| `type: "quick-service-grid"` | نمایشگر ازپیش‌ساختهٔ میانبرها؛ نوع چیدمان سریع‌دسترسی را انتخاب می‌کند. |
| `order: 30` در `card-quick-actions` | میانبرها پس از دو بخش قبلی نمایش داده می‌شوند. |
| `serviceIds: ["card-block", "card-unblock"]` | سرویس مسدودکردن کارت و سپس رفع مسدودی را در این بخش می‌آورد؛ ترتیب آرایه ترتیب همین دو مورد است. |

برای کوتاه نگه‌داشتن JSON، `services[]` در نمونه کامل نیست و تعریف پنج شناسهٔ کارت در بدنهٔ نمونه نیامده است. این سرویس‌ها را در جدول زیر توضیح داده‌ایم؛ پاسخ واقعی باید برای همهٔ این شناسه‌ها یک تعریف متناظر در `services[]` داشته باشد.

معنای شناسه‌های سرویس نمونه:

| شناسه | سرویس مورد نظر |
|---|---|
| `card-issue` | درخواست صدور کارت |
| `card-password` | خدمات رمز کارت |
| `card-virtual` | درخواست کارت مجازی |
| `card-block` | مسدودکردن کارت |
| `card-unblock` | رفع مسدودی کارت |

این شناسه‌ها باید در فهرست `services[]` تعریف شوند؛ اگر در نمونهٔ کوتاه پاسخ، تعریف کاملشان درج نشده باشد، باید صریحاً گفته شود که بخش تعریف سرویس‌ها خلاصه شده است. در قرارداد نهایی، هیچ `serviceId` ارجاع‌داده‌شده‌ای نباید بدون تعریف بماند.

| `schemaVersion` | بله | نسخهٔ ساختار دادهٔ `JSON`؛ اپ با آن می‌سنجد که قالب پاسخ را می‌شناسد یا نه. | نسخهٔ ناشناخته اعمال نشود؛ اپ از نسخهٔ ذخیره‌شده یا فهرست محلی استفاده کند. |

### ۵.۲ تب و بخش‌های داخل آن

| فیلد | الزامی | چه چیزی را مشخص می‌کند؟ | قاعدهٔ استفاده |
|---|---:|---|---|
| `tabs[].id` | بله | شناسهٔ یکی از چهار تب `dashboard`, `cards`, `deposits`, `loans`. | در نسخهٔ فعلی تب جدید قابل‌ساخت نیست؛ شناسهٔ ناشناخته نادیده گرفته شود. |
| `tabs[].order` | بله | جایگاه تب در نوار اصلی؛ عدد صحیح با فاصله، مثلاً 10، 20، 30، 40. | ترتیب نهایی بر اساس عدد صعودی است؛ مقدارهای برابر با شناسه شکسته شوند. |
| `tabs[].visible` | بله | آیا تب در نوار اصلی نمایش داده شود. | برای چهار تب فعلی، پنهان‌کردن تب باید پیش از پیاده‌سازی با محصول و مسیرهای بازگشت توافق شود؛ سرور نباید باعث از دسترس خارج‌شدن همهٔ تب‌ها شود. |

| `sections[].type` | بله | نوع نمایش از فهرست بخش‌های پیاده‌شدهٔ اپ؛ مثل `service-grid` یا `cards-carousel`. | نوع ناشناخته نمایش داده نشود؛ سایر بخش‌های معتبر صفحه باقی بمانند. |
| `sections[].titleKey` | بسته به نوع | کلید متن ثابت اپ برای عنوان بخش؛ نمونه: `cards.operations`. | اگر نوع نمایش به عنوان نیاز دارد، اپ از متن محلی `S.current` استفاده کند یا بخش را با عنوان پیش‌فرض نشان دهد. |
| `sections[].order` | بله | ترتیب بخش در همان تب. | بخش‌های معتبر با ترتیب پایدار مرتب شوند. |
| `sections[].serviceIds` | برای بخش سرویس | شناسه‌های سرویس‌هایی که باید در این بخش و به همان ترتیب نشان داده شوند. | شناسهٔ ناشناخته یا ناسازگار با شمارهٔ ساخت اپ نمایش داده نشود؛ بقیهٔ آیتم‌ها باقی بمانند. |
| `sections[].dataSource` | برای بخش داده‌ای | نام منبع دادهٔ شناخته‌شدهٔ اپ؛ مثل `customer-cards`. | مقدار ناشناخته پذیرفته نشود؛ اپ برای همان بخش پیام/نمایش جایگزین نشان دهد و نشانی دلخواه سرور را اجرا نکند. |

پیشنهاد می‌شود چهار تب اصلی در اپ ثابت بمانند و Backend فقط ترتیب و محتوای داخل آن‌ها را کنترل کند. حذف یا جابه‌جایی تب‌ها تصمیم محصولی است و باید با مسیرهای ناوبری اپ هماهنگ شود.

### ۵.۳ اطلاعات هر سرویس

| فیلد | الزامی | چه چیزی را مشخص می‌کند؟ | اگر نباشد یا معتبر نباشد |
|---|---:|---|---|
| `services[].id` | بله | شناسهٔ ثابت و یکتای سرویس؛ از عنوان، آیکن و مسیر مستقل است. این شناسه در تب‌ها و Drawer ارجاع داده می‌شود. | سرویس بدون شناسه قابل‌نمایش/اجرا نیست؛ حذف شود و خطای داده گزارش شود. |
| `titleKey` | یکی از این یا `titles` | کلید ترجمه‌ای که نسخهٔ اپ می‌شناسد؛ متن از `S.current` نمایش داده می‌شود. برای سرویس‌های ثابت روش ترجیحی است. | اگر `titles` معتبر هم نباشد، سرویس عنوان قابل‌نمایش ندارد و باید حذف/غیرفعال شود. |
| `titles` | یکی از این یا `titleKey` | متن سرویس به ازای زبان‌ها، برای سرویس واقعاً پویا؛ نمونه: `fa-IR` و `en-US`. | اپ ابتدا زبان کاربر و سپس زبان جایگزین توافق‌شده را می‌جوید؛ اگر هیچ‌کدام نبود، سرویس بدون متن نباید به‌صورت قابل‌اجرا نشان داده شود. |
| `description` | خیر | توضیح کوتاه سرویس به زبان‌های پشتیبانی‌شده؛ فقط اگر UI محل نمایش آن را دارد. | نادیده گرفته شود؛ نبودن توضیح نباید مانع نمایش سرویس شود. |
| `icon.url` | بله | نشانی فایل تصویر که سرویس تصویر در اختیار اپ می‌گذارد؛ باید `HTTPS` و روی میزبان مجاز باشد. | نشانی نامعتبر/ناامن رد شود و آیکن جایگزین عمومی اپ نمایش داده شود؛ سرویس به‌خاطر خرابی تصویر حذف نشود. |
| `icon.format` | بله | قالب واقعی تصویر، مثل `svg`, `png`, `webp`. | قالب ناشناخته/ناسازگار رد شود؛ نوع واقعی محتوا نیز بررسی شود. |
| `icon.version` یا `icon.sha256` | پیشنهاد می‌شود | راه تشخیص نسخهٔ تصویر برای مدیر ذخیره‌سازی. `sha256` اثرانگشت دقیق فایل است؛ `version` باید با هر تغییر تصویر عوض شود. | اگر هیچ‌کدام نباشد، مدیر ذخیره‌سازی از URL به‌عنوان کلید استفاده می‌کند و تغییر تصویر باید URL تازه داشته باشد. |
| `visible` | بله | آیا سرویس در این کاتالوگ نمایش داده شود. | مقدار ناشناخته به‌صورت پیش‌فرض نمایش داده نشود. |
| `enabled` | بله | آیا کنترل سرویس در صفحه قابل انتخاب باشد؛ مثلاً برای عرضهٔ مرحله‌ای یا محدودیت نمایشی. | مقدار نامعتبر غیرفعال در نظر گرفته شود. این فیلد مجوز واقعی کاربر نیست. |
| `requiredContext` | در صورت نیاز | داده‌ای که اپ باید از کاربر یا صفحهٔ فعلی بگیرد؛ مثل `selectedDeposit`. | اگر داده فراهم نبود، اپ مرحلهٔ انتخاب را نشان دهد یا سرویس را غیرفعال کند؛ درخواست بانکی ناقص ارسال نشود. |
| `minimumBuild` | خیر | کمترین شمارهٔ ساخت اپی که این سرویس یا مقصد آن را می‌شناسد. | اگر شمارهٔ ساخت نصب‌شده پایین‌تر باشد، سرویس نمایش داده یا اجرا نشود. |
| `action` | بله | تعریف می‌کند کلیک کاربر چه مقصد پشتیبانی‌شده‌ای را اجرا کند. | اگر نوع یا مقصد ناشناخته باشد، اپ مقصد جایگزین حدس نمی‌زند؛ آیتم غیرفعال/حذف می‌شود. |

برای متن‌های ثابت اپ، `titleKey` به شناسهٔ ترجمهٔ شناخته‌شده وصل می‌شود و متن از `S.current` می‌آید. اپ نام تابع ترجمه را از سرور نمی‌گیرد و اجرا نمی‌کند. برای سرویس‌های پویا، `titles` متن چندزبانه می‌دهد و ترتیب زبان جایگزین باید در قرارداد مشخص شود.

با فرض دریافت همهٔ تصویرها از سرویس، `iconKey` وارد پاسخ نمی‌شود. Image Cache Manager برای cache از `sha256` استفاده می‌کند؛ اگر نبود، از ترکیب URL و `version` استفاده می‌کند. پس یک شناسهٔ جدا برای پیدا کردن تصویر در اپ، دادهٔ تکراری خواهد بود. URLها باید پایدار باشند یا هنگام تغییر فایل، نسخهٔ تصویر/URL عوض شود.

### ۵.۴ تعیین مقصد هنگام انتخاب سرویس

برای مشخص‌کردن صفحه‌ای که با انتخاب سرویس باز می‌شود، دو روش قابل‌بررسی است. در هر دو روش، `id` سرویس ثابت می‌ماند و برای چیدمان، جستجو و علاقه‌مندی‌ها استفاده می‌شود. تفاوت فقط در تعریف مقصد است: در روش اول اپ مقصد را از روی شناسه پیدا می‌کند؛ در روش دوم Backend route را هم می‌فرستد.

#### روش اول — ارسال شناسهٔ سرویس و تعیین مقصد در اپ

```json
{
  "id": "card-virtual",
  "titleKey": "dashboardVirtualCard",
  "action": { "kind": "native_service", "serviceId": "card-virtual" }
}
```

اپ `serviceId` را در فهرست مقصدهای مجاز خودش پیدا می‌کند؛ در پروژه این نگاشت با `DashboardService` و `ServiceRegistry` انجام می‌شود. سپس اپ مسیر و ورودی‌های لازم صفحه را با نوع مشخص می‌سازد.

**مزایا:** مسیرهای داخل اپ از API مستقل می‌مانند؛ تغییر مسیر فقط در اپ مدیریت می‌شود؛ ورودی‌هایی مثل سپرده یا کارت انتخاب‌شده با نوع مشخص ساخته می‌شوند.  
**محدودیت:** سرویس جدیدی که در خود اپ پیاده شده باشد باید در نسخهٔ نصب‌شده شناخته شود؛ Backend نمی‌تواند در نسخهٔ قدیمی مقصدی را فعال کند که اپ نمی‌شناسد.

#### روش دوم — ارسال route از Backend

```json
{
  "id": "card-virtual",
  "titleKey": "dashboardVirtualCard",
  "action": {
    "kind": "native_route",
    "routePath": "/cards/virtual-request",
    "queryParameters": {},
    "routeArguments": {
      "schema": "card-route-v1",
      "context": "selected-deposit-and-card"
    }
  }
}
```

نمونهٔ مسیرهای فعلی اپ: `/dashboard/home`، `/cards/virtual-request`، `/cards/issuance`، `/deposits/average-balance` و `/requests/reports`. مقدار `routePath` باید دقیقاً با یکی از مسیرهای همان نسخهٔ اپ برابر باشد. اگر صفحه ورودی اضافه‌ای لازم دارد، `routeArguments.schema` مشخص می‌کند اپ کدام قالب ورودی را بسازد. فرستادن مسیر به‌تنهایی برای صفحه‌ای که به سپرده یا کارت انتخاب‌شده نیاز دارد کافی نیست.

**مزیت:** مقصد در پاسخ Backend آشکار است و ترتیب و مقصد سرویس از یک فهرست خوانده می‌شوند.  
**محدودیت:** قرارداد API به مسیرهای داخلی اپ وابسته می‌شود. تغییر نام یا حذف مسیر می‌تواند فهرست نسخه‌های نصب‌شده را خراب کند؛ برای هر تغییر باید سازگاری نسخه‌های قدیمی بررسی شود.

**قاعدهٔ ایمنی:** اپ نباید مقدار `routePath` را بدون بررسی به `context.go` یا `context.push` بدهد. مسیر باید با فهرست دقیق مسیرهای مجاز همان نسخه تطبیق داده شود. مسیر ناشناخته، مسیر ورود/احراز هویت، نشانی اینترنتی بیرونی و مقدارهای نامعتبر رد شوند. توکن یا اطلاعات محرمانه در `queryParameters` قرار نگیرد. برای صفحهٔ نیازمند سپرده یا کارت، Backend فقط نوع نیاز را اعلام کند؛ خود اپ دادهٔ انتخاب‌شده را در ورودی صفحه قرار دهد.

پارامترهای روش دوم:

| فیلد | الزامی | چه چیزی را مشخص می‌کند؟ | قاعدهٔ بررسی در اپ |
|---|---:|---|---|
| `routePath` | بله | مسیر داخلی مقصد؛ برای نمونه `/cards/virtual-request`. | باید دقیقاً با یک مسیر مجاز در نسخهٔ اپ برابر باشد؛ مسیر ناشناخته یا محافظت‌شده رد شود. |
| `queryParameters` | خیر | مقدارهای ساده و غیرمحرمانه‌ای که به نشانی افزوده می‌شوند؛ برای نمونه `category=resalat`. | فقط کلیدها و مقدارهای مجاز همان مسیر پذیرفته شوند؛ اندازه و نوع مقدار بررسی شود. |
| `routeArguments.schema` | در صورت نیاز | شناسهٔ نسخه‌دار قالب ورودی که اپ می‌شناسد؛ برای نمونه `card-route-v1`. | فقط قالب ثبت‌شده پذیرفته شود؛ دادهٔ آزاد مستقیم به صفحه داده نشود. |
| `routeArguments.context` | در صورت نیاز | اعلام می‌کند صفحه به کدام دادهٔ جریان فعلی نیاز دارد؛ برای نمونه `selected-deposit-and-card`. | اپ دادهٔ لازم را از وضعیت/انتخاب کاربر می‌گیرد؛ اگر موجود نبود، مرحلهٔ انتخاب را نشان می‌دهد. |

#### مقصدهای دیگر در نسخه‌های آینده

| `action.kind` | فیلد اصلی | رفتار اپ |
|---|---|---|
| `micro_app` | `targetId` | اجرای برنامهٔ کوچک درون اپ که از قبل ثبت و پشتیبانی شده باشد؛ قرارداد نشست کاربر و چرخهٔ اجرا جداگانه لازم است. |
| `web_view` | `targetId` یا `contentId` | نمایش محتوای وب از میزبان مجاز؛ رفتار ورود، پیوندهای بیرونی و پل ارتباطی با اپ باید مشخص باشد. |
| `bottom_sheet` | `targetId` | بازکردن Bottom Sheet از پیش پیاده‌شده با شناسهٔ ثابت؛ Backend ظاهر دلخواه نمی‌سازد. |
| `tab` | `targetId` | رفتن به یکی از چهار تب شناخته‌شدهٔ اپ. |

نمونهٔ Bottom Sheet:

```json
{
  "kind": "bottom_sheet",
  "targetId": "deposit-filter",
  "parameters": { "filterPreset": "active" }
}
```

در روش اول، `serviceId` فقط وقتی پذیرفته شود که اپ آن را بشناسد. در روش دوم، `routePath` باید دقیقاً در فهرست مسیرهای مجاز باشد. مقصد ناشناخته در هر دو روش غیرفعال یا حذف می‌شود؛ اپ نباید آن را به مقصد دیگری بفرستد. Backend نباید نام کلاس `Dart`، نام ویجت، `HTML` یا `JavaScript` اجرایی ارسال کند.

برای نمایش وب، میزبان‌های مجاز، `HTTPS`، نحوهٔ انتقال نشست، مجوزهای پل ارتباطی، رفتار دکمهٔ بازگشت و بازکردن پیوند بیرونی باید جداگانه تصویب شوند. نشانی دریافت‌شده از API بدون بررسی باز نشود و توکن بانکی در پارامترهای نشانی قرار نگیرد.

### ۵.۵ شناسه‌ها و تغییر مسیر

- شناسهٔ سرویس با تغییر عنوان، آیکن، جایگاه یا مسیر ثابت بماند.
- شناسه‌ها مثل `DashboardService.id` کوتاه، یکتا و پایدار باشند؛ برای سرویس تازه شناسهٔ تازه تعریف شود.
- در روش اول، تغییر مقصد فقط نگاشت داخل اپ را عوض می‌کند و `serviceId` ثابت می‌ماند.
- در روش دوم، `routePath` بخشی از قرارداد نسخه‌دار API می‌شود. پیش از حذف یا تغییر مسیر، برای نسخه‌های قدیمی نام جایگزین سازگار یا فهرست جدا در نظر گرفته شود.
- تغییر معنای شناسهٔ سرویس یا مسیر قبلی ناسازگار است؛ برای رفتار تازه شناسه یا قالب تازه تعریف شود.
- `parameters` هر مقصد باید قالب محدود و مشخص داشته باشد. دادهٔ آزاد Backend مستقیم به سازندهٔ صفحه یا ورودی مسیریابی داده نشود.

## ۶. Drawer: همان پاسخ یا دریافت جداگانه؟

### پیشنهاد فعلی: چیدمان منو در پاسخ Page Builder

صفحهٔ خانه و Drawer معمولاً به سرویس‌های یکسان اشاره می‌کنند و باید با یک انتشار هماهنگ شوند. اگر `drawer.items` در همان پاسخ باشد، هر دو از یک `catalogVersion` و یک تعریف مشترک عنوان، آیکن و مقصد استفاده می‌کنند. گروه‌بندی و ترتیب منو می‌تواند با ترتیب سرویس‌ها در تب‌ها فرق داشته باشد؛ هر زیرآیتم فقط با `serviceId` به تعریف سرویس ارجاع می‌دهد.

### چه زمانی دریافت جداگانه توجیه دارد؟

- مالک یا زمان انتشار منو واقعاً مستقل باشد.
- اندازهٔ پاسخ یا نیاز ذخیره‌سازی موقت دلیل عملیاتی روشنی برای جداسازی داشته باشد.
- پاسخ جدا فقط شناسهٔ گروه، ترتیب و `serviceId`ها را بدهد؛ عنوان، آیکن و مقصد سرویس دوباره تعریف نشوند.
- هر دو پاسخ نسخهٔ سازگار داشته باشند. اگر نسخه‌ها با هم نخواند، اپ آخرین جفت سازگار یا فهرست محلی را استفاده کند.

با ساختار فعلی پروژه، دریافت جدا برای منو پیشنهاد نمی‌شود؛ مگر تیم Backend نیاز عملیاتی مشخصی ارائه کند.

### پیشنهاد گروه‌های اولیهٔ Drawer

ساختار فعلی اپ این گروه‌ها را دارد؛ نام و ترتیب نهایی باید در جلسه با مالک محصول تأیید شود:

1. خانه
2. بانکداری مدرن
3. کارت‌ها
4. چک
5. انتقال وجه
6. وام
7. سپرده
8. کیف پول
9. اطلاعات هویتی
10. درخواست‌ها

فیلدهای پیشنهادی گروه و زیرآیتم:

| فیلد | محل استفاده | معنا | اگر نامعتبر باشد |
|---|---|---|---|
| `drawer.items[].id` | گروه منو | شناسهٔ پایدار گروه، مثل `cards` یا `requests`. | گروه تکراری یا بدون شناسه حذف شود. |
| `drawer.items[].order` | گروه و زیرآیتم | ترتیب نمایش؛ عدد کوچک‌تر زودتر دیده می‌شود. | مرتب‌سازی پایدار با شناسه انجام شود. |
| `titleKey` یا `titles` | گروه و زیرآیتم مستقل | `titleKey` متن ثابت محلی اپ را انتخاب می‌کند؛ `titles` نام چندزبانهٔ محتوای پویا را می‌دهد. | اگر متن قابل‌نمایش پیدا نشد، گروه/آیتم نشان داده نشود. |
| `icon` | گروه | مشخصات تصویر گروه از سرویس تصویر؛ همان ساختار `url`, `format` و `version` که برای سرویس‌ها استفاده می‌شود. | اگر تصویر نامعتبر یا دریافت‌ناپذیر بود، اپ آیکن عمومی جایگزین نشان دهد. |
| `children[].serviceId` | زیرآیتم سرویس | پیوند به یک تعریف در `services[]`؛ عنوان و مقصد را از همان تعریف می‌گیرد. | شناسهٔ ناشناخته حذف شود. |
| `action` | گروهی که خودش مقصد دارد | مقصد شناخته‌شده، مثل رفتن به تب خانه یا فهرست درخواست‌ها. | فقط عملیات ثبت‌شده پذیرفته شوند. |
| `visible` | گروه/آیتم | نمایش یا پنهان‌کردن در منو. | مقدار نامعتبر به‌صورت پنهان در نظر گرفته شود. |

جستجوی منو داخل اپ و بر اساس عنوان‌های نمایش‌داده‌شده انجام شود؛ برای هر حرفی که کاربر تایپ می‌کند درخواست جدا به Backend لازم نیست.

## ۷. اعتبارسنجی، جایگزین و ذخیرهٔ موقت

1. اپ نسخهٔ ساختار `schemaVersion` و نوع‌های بخش/مقصدی را که می‌شناسد بررسی کند.
2. فیلد افزودهٔ اختیاری که اپ نمی‌شناسد نادیده گرفته شود. اگر ساختار الزامی ناسازگار است، پاسخ اعمال نشود.
3. شناسهٔ تکراری، ترتیب نامعتبر، فهرست بیش‌ازحد بزرگ و زبان ناپشتیبانی‌شده باید رفتار مشخص داشته باشند.
4. اگر `minimumBuild` از شمارهٔ ساخت نصب‌شده بالاتر است، سرویس نباید قابل‌اجرا باشد.
5. مجوز یا قابلیت ارسالی فقط برای نمایش آیتم است؛ API عملیاتی هنگام درخواست باید مجوز واقعی را دوباره بررسی کند.
6. اگر دریافت فهرست شکست خورد، اپ آخرین نسخهٔ معتبر ذخیره‌شده را نشان دهد؛ اگر نسخه‌ای ندارد، از فهرست محلی حداقلی استفاده کند. خرابی یک آیکن نباید کل صفحهٔ خانه را خالی کند.
7. برای `ETag`, `expiresAt`, مدت نگهداری و کارکرد آفلاین توافق شود. پاسخ وابسته به کاربر در حافظهٔ عمومی ذخیره نشود.
8. تصویر با `sha256` یا ترکیب URL و `version` در Image Cache Manager شناخته شود. میزبان، نوع محتوا، مهلت دریافت، اندازه و آیکن جایگزین مشخص باشند؛ فایل `SVG` یا `HTML` به‌عنوان کد اجرا نشود.
9. سه سرویس مسئولیت جدا دارند: Page Builder چیدمان را می‌دهد؛ `Remote Config` مقدارهای رفتاری را می‌دهد؛ `Update Manager` سیاست نسخهٔ اپ را تعیین می‌کند.

## ۸. تصمیم‌های لازم برای پاسخ کامل و رفتار خطا

پیشنهاد می‌شود endpoint کاتالوگ برای همان اپ/پلتفرم یک پاسخ کامل از کاتالوگ فعال بدهد؛ پاسخ incremental یا patch نباشد، مگر اینکه قرارداد مستقل merge و حذف آیتم‌ها تعریف شود. در پاسخ کامل، نبودن یک تب/گروه/سرویس یعنی آن مورد در نسخهٔ فعال وجود ندارد. این قاعده جلوی باقی‌ماندن آیتم حذف‌شده در cache را می‌گیرد.

رفتارهای پیشنهادی:

| وضعیت | رفتار سرور | رفتار اپ |
|---|---|---|
| کاتالوگ تازه | 200 همراه بدنه و ETag | اعتبارسنجی کامل، سپس جایگزینی کاتالوگ قبلی |
| کاتالوگ بدون تغییر | 304 و بدنهٔ خالی | نگه‌داشتن نسخهٔ ذخیره‌شده |
| پارامتر یا appId ناشناخته | خطای 4xx با کد پایدار | نمایش کاتالوگ معتبر ذخیره‌شده یا محلی؛ عدم تفسیر خطا به‌عنوان فهرست خالی |
| خطای موقت Backend/شبکه | 5xx یا خطای شبکه | استفاده از آخرین کاتالوگ معتبر تا مهلت cache توافق‌شده |
| پاسخ JSON/schema ناسازگار | پاسخ خطادار و ثبت پایش در سرور | رد کل snapshot ناسازگار و حفظ آخرین نسخهٔ معتبر |
| آیتم اختیاری خراب/ناشناخته | ترجیحاً حذف/اصلاح از سمت سرور | رد همان آیتم و نگه‌داشتن سایر موارد معتبر |

پیش از تحویل API، قرارداد باید اندازهٔ بیشینهٔ پاسخ، تعداد مجاز تب/بخش/سرویس، زمان cache آفلاین، قالب خطا (code و requestId)، rate limit، احراز هویت، سیاست پاسخ شخصی‌سازی‌شده و زمان انتشار/rollback کاتالوگ را مشخص کند. ETag باید با محتوای مؤثر همان کاربر/پلتفرم/نسخه یکی‌به‌یکی سازگار باشد؛ پاسخ دو کاربر متفاوت نباید با ETag مشترک و cache مشترک اشتباه شود.

### فهرست نوع‌های نسخهٔ اول

پیشنهاد نسخهٔ اول، فقط این نوع‌ها را در قرارداد فعال کند:

| مقدار | دادهٔ مورد نیاز | تفسیر اپ |
|---|---|---|
| service-grid | titleKey و serviceIds | شبکهٔ سرویس‌ها با عنوان بخش |
| quick-service-grid | serviceIds | شبکهٔ میانبرها با ظاهر ازپیش‌تعریف‌شدهٔ اپ |
| cards-carousel | dataSource=customer-cards | درخواست داده از جریان/مخزن کارت و نمایش پیمایشی کارت‌ها |
| deposits-carousel | dataSource=customer-deposits | درخواست داده از جریان/مخزن سپرده و نمایش پیمایشی سپرده‌ها |
| loans-carousel | dataSource=customer-loans | درخواست داده از جریان/مخزن وام و نمایش پیمایشی وام‌ها |

در نسخهٔ اول، dataSource فقط انتخابگر یک مقدار ثابت در allowlist اپ است؛ نه URL، مسیر سرویس یا نام متدی که سرور بتواند اجرا کند. نوع ناشناخته یا ترکیب فیلد ناسازگار باید همان بخش را نامعتبر کند، نه اینکه اپ نمایشگر دیگری را حدس بزند.

## ۹. پیشنهاد مرحله‌بندی

### مرحلهٔ ۱ — قابلیت‌های قابل‌پیاده‌سازی در اپ فعلی

- چهار تب ثابت.
- ترتیب بخش‌ها و شناسه‌های سرویس موجود.
- انتخاب رسمی یکی از دو روش مقصد (`serviceId` یا `routePath`)؛ روش دیگر به‌عنوان گزینهٔ مهاجرت یا مرحلهٔ بعد باقی بماند.
- URL تصویرهای سرویس با `format` و `version`/`sha256`، عنوان‌های شناخته‌شده و مقصدهای بومی فهرست‌شده در اپ.
- چیدمان منو در همان پاسخ، با ارجاع به `serviceId`.
- نسخهٔ ساختار و محتوا، `expiresAt` و `ETag`، رفتار آفلاین و کدهای خطا.

### مرحلهٔ ۲ — محتوای منعطف‌تر

- عنوان و توضیح چندزبانهٔ ارسالی سرور برای سرویس‌های واقعاً پویا.
- مدیر دریافت و ذخیره‌سازی تصویر با میزبان مجاز و بررسی اثرانگشت/نسخه.
- دلیل غیرفعال‌بودن، نشان اطلاع‌رسانی و اشاره به شرایط دسترسی؛ همراه با تعریف روشن تجربهٔ کاربر.

### مرحلهٔ ۳ — مقصدهای جدید

- `web_view`, `bottom_sheet`, `micro_app` فقط بعد از توافق امنیت، نشست کاربر، فهرست مقصدهای مجاز، رفتار بازگشت و پشتیبانی اجرایی اپ.
- مقصد ناشناخته تا قبل از انتشار نسخهٔ پشتیبان نباید نسخه‌های قدیمی را از کار بیندازد.
