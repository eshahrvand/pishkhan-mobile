# Change linked card deposit

Status: implemented with an injectable repository and illustrative in-memory data. No bank operation or wallet debit is performed by the default adapter.

## Design and entry points

All references belong to the [Cards Figma design](https://www.figma.com/design/nYQNyZdSs98lwymCpt5Sag/Pishkhan-AI-Mobile?node-id=27997-10143).

| State | Node |
| --- | --- |
| Empty form | `27997:10143` |
| Card selected, destination empty | `27997:10849` |
| Destination and consent filled | `27997:10873` |

The authenticated route is `/cards/change-deposit` (`CardsRoutes.changeDeposit`). Service ID `card-deposit` opens it from the dashboard service catalog, the dashboard card action, and the standalone card action sheet. Explicit host action callbacks retain precedence. `CardRouteArguments.initialCardNumber` carries selected-card context; a matching repository card is selected after loading. Unknown card numbers leave the selector empty rather than inventing a bank record.

## Behavior and state ownership

`ChangeCardDepositCubit` owns loading, selected card, destination eligibility, consent, submission and failures. The current deposit is derived from the selected card and displayed read-only. The destination list excludes that deposit. Changing a card resets destination and consent; changing destination resets consent. Submission requires a known card and destination, accepted terms and sufficient wallet balance. Loading submissions disable editing, back navigation and duplicate submission.

The initial empty design is an unselected form with loaded options, distinct from a genuinely empty catalog. Empty catalogs, loading and load failures have dedicated UI states with retry. A failed submission leaves the form editable. An unchanged retry retains its idempotency key; editing the request creates a new key. Superseded loads and responses after Cubit disposal are ignored.

The terms action delegates to the optional host callback. Without one, the app reports that the terms document is unavailable. Completion delegates to the optional receipt callback and displays an explicitly marked demo receipt when using the mock adapter.

## Data and integration

The category-level `CardServicesRepository` is shared with the [expired gift balance flow](expired-gift-balance.md). Its domain entities and requests live in `lib/features/cards/domain/`; `LoadCardServiceCatalog` validates IDs, deposit references and nonnegative monetary values, and adapter exceptions become `Failure` values.

`MockCardServicesRepository` supplies two accounts, selectable cards, a 1,300,000-rial illustrative fee and a 2,000,000-rial wallet balance. It also resolves the existing dashboard demo card. Fees are supplied by the adapter, not inferred from a bank tariff. Replace the repository when authoritative catalogs, eligibility, fees, terms and execution endpoints are available. The mock receipt cache only deduplicates calls in memory and does not persist or change balances or card linkage.

## UI composition

The screen supplies a `BlocProvider` whose `create` constructs the Cubit and calls `load()`. The provider closes it on removal and preserves it across ordinary rebuilds. Changing the repository or initial card starts a new provider scope. UI reads status and step directly from State. The Cubit computes selected records, empty-data state and action eligibility before emitting immutable State fields; no custom getters are defined. The view owns navigation and completion effects; the form owns the substantial input/invoice section. Inputs use `avp_ui` `AppSelect` directly, including the disabled current-deposit field. Buttons and checkboxes also come from `avp_ui`; the existing app invoice and top bar are reused. Shared request footer/status/spacing components are grouped under `presentation/shared/`, rather than creating a file per label or field. Handwritten UI files follow the widget skill's approximate 200-line target and allow cohesive sections around 200–300 lines.

All new copy is localized in the Persian, English and Arabic ARBs. App controls remain RTL in every locale; card display grouping uses the package formatter. Original Figma helper icons are bundled locally; runtime code has no temporary Figma URLs.

## Validation

Cubit tests cover selection/reset rules, seeded card normalization, wallet gating, adapter failures, request deduplication, safe retry and stale/disposed responses. Widget tests exercise all three design states, submission failure/retry, service navigation and selected-card context. The shared Stepper has a regression test for right-aligned labels and dot spacing in the related gift flow.

## Cubit/State coding convention

Follow [architecture Section 12](../architecture-smart-virtual-counter-v2-en.md#12-state-management-with-cubit) for new work and refactors. State is a plain Freezed data class with defaults and independent request statuses. Cubits accept an initial State, compute UI data and eligibility, and emit immutable snapshots through `copyWith`. UI reads those fields directly; no custom State/Cubit getters or UI-facing rules facade is used. Dependencies remain injectable and lifecycle/duplicate-request safeguards stay in place.
