# بررسی فعال‌بودن دکمهٔ درخواست رمز و API دکمهٔ avp_ui

تاریخ: ۲۰۲۶/۱۰/۱۵  
وضعیت: بررسی و پیشنهاد؛ پیاده‌سازی برنامه و پکیج تغییر نکرده است.

## پاسخ مستقیم

برای فعال و غیرفعال شدن دکمهٔ درخواست رمز، State جدید یا فیلد تکراری لازم نیست. فیلد `formValid` در `AuthState` وجود دارد، مقدار پیش‌فرضش `false` است و در اکشن‌های تغییر کد ملی، موبایل و کپچا محاسبه می‌شود. مشکل فعلی، وصل‌نبودن دکمه به این فیلد است.

در API فعلی `AppButton`، ورودی `isLoading` موجود است؛ `isActive` وجود ندارد. غیرفعال کردن دکمه اکنون با `onPressed: null` انجام می‌شود. اگر سبک مطلوب پروژه کنترل با دو ورودی مستقل باشد، پیشنهاد مشخص این گزارش افزودن `isActive` با پیش‌فرض `true` در خود `avp_ui` و حفظ `isLoading` موجود است.

اکشن‌های `updateNationalId`، `updatePhoneNumber` و `updateCaptcha` مقدار تازهٔ ورودی و نتیجهٔ `checkFormValid` را در یک `emit` قرار می‌دهند. شرط فعلی اعتبار فرم چنین است:

<pre dir="ltr">NationalCodeValidator.isValid(nationalId) &amp;&amp;
PhoneNumberValidator.isValid(phone) &amp;&amp;
CodeValidator.isValid(captcha, length: 6)</pre>

معنای این شرط:

- کد ملی: ۱۰ رقم لاتین، غیرتکراری و دارای checksum معتبر طبق validator مرکزی.
- شماره موبایل: ۱۱ رقم لاتین با شروع `09`.
- کپچا: دقیقاً ۶ رقم لاتین؛ صحت پاسخ تصویر در این مرحله مشخص نیست.

این بررسی‌ها، وجود واقعی کد ملی، مالکیت شماره همراه یا تطابق مالک شماره با کد ملی را ثابت نمی‌کنند. بررسی‌های سرور باید جداگانه انجام شوند.

### علت فعال‌بودن فعلی دکمه

در `AuthIdentityForm`، دکمه همیشه یک callback غیر null دریافت می‌کند و برای خودش اشتراک مرتبطی با `formValid` ندارد. به همین دلیل حتی با فرم خالی، فعال دیده می‌شود و کلیک را می‌پذیرد؛ سپس `requestOtp()` ورودی‌ها را بررسی و خطاها را ثبت می‌کند.

صرف تغییر مقدار `formValid`، بدون مصرف آن در builder دکمه، ظاهر و تعامل دکمه را تغییر نمی‌دهد.

## ۲. وضعیت موجود AppButton

منبع واقعی خوانده‌شده: `C:/Users/mahdi/StudioProjects/avp_ui/lib/widgets/buttons/app_button.dart`، از پکیج محلی‌ای که برنامه به آن وابسته است.

| قابلیت | وضعیت فعلی |
| --- | --- |
| `isLoading` | موجود، با مقدار پیش‌فرض `false` |
| `isActive` | موجود نیست |
| غیرفعال شدن | با `onPressed: null` |
| جلوگیری از کلیک هنگام loading | موجود |
| نمایش loading | نمایش spinner به جای محتوای عادی |
| ظاهر disabled | رنگ متن و سطح غیرفعال از توکن‌های پکیج |
| ظاهر جایگزین disabled | با `disabledAppearance`؛ این ورودی فقط ظاهر را تنظیم می‌کند |

شرط فعال‌بودن داخلی دکمه اکنون چنین است:

<pre dir="ltr">onPressed != null &amp;&amp; !isLoading</pre>

پس پکیج همین حالا رفتار غیرفعال و loading را پشتیبانی می‌کند؛ ورودی نام‌دار `isActive` برای ساده‌تر شدن کنترل در محل مصرف، یک تغییر API پیشنهادی است.

تست موجود پکیج در `test/widgets/app_button_test.dart` شامل بررسی جلوگیری از اجرای callback هنگام loading و حفظ ظاهر disabled است. در این نوبت فقط کد تست‌ها خوانده شد و اجرا نشدند.

## ۳. پیشنهاد API با دو ورودی

برای سازگاری با مصرف‌کنندگان فعلی:

<pre dir="ltr">this.isActive = true,
this.isLoading = false,

final bool isActive;
final bool isLoading;</pre>

شرط مؤثر تعامل در پکیج:

<pre dir="ltr">isActive &amp;&amp; onPressed != null &amp;&amp; !isLoading</pre>

این پیشنهاد، `onPressed` فعلی را nullable نگه می‌دارد. بنابراین مصرف‌کنندگان موجود که با null دکمه را غیرفعال می‌کنند، رفتار خود را حفظ می‌کنند و مهاجرت هم‌زمان همهٔ دکمه‌ها لازم نمی‌شود.

### قرارداد رفتار پیشنهادی

| isActive | isLoading | callback | رفتار |
| --- | --- | --- | --- |
| false | false | موجود یا null | غیرفعال، با ظاهر disabled و بدون اجرای callback |
| true | false | موجود | فعال و قابل کلیک |
| true | false | null | غیرفعال؛ سازگار با قرارداد قبلی |
| true یا false | true | موجود یا null | نمایش loading و جلوگیری از کلیک |

هنگام `isLoading: true`، نمایش loading اولویت دارد؛ لازم نیست caller برای نشان‌دادن spinner مقدار `isActive` را اجباراً true کند. وضعیت accessibility و مسیر کلیک نیز باید از همین شرط مؤثر پیروی کنند تا دکمه فقط از نظر رنگ غیرفعال نباشد.

پکیج، اعتبار فرم را محاسبه نمی‌کند؛ فقط مقادیر دریافتی را به ظاهر و تعامل تبدیل می‌کند.

## ۴. اتصال پیشنهادی در فرم ورود

بعد از اضافه‌شدن واقعی `isActive` به پکیج، مصرف دکمه می‌تواند با مقادیر مستقیم State باشد:

<pre dir="ltr">isActive: state.formValid,
isLoading: state.status == RequestStatus.loading,</pre>

این نمونه پیشنهاد اتصال است؛ پارامتر `isActive` اکنون در پکیج موجود نیست و نباید پیش از تغییر پکیج در کد برنامه استفاده شود.

دکمه در یک `BlocBuilder` مرتبط قرار می‌گیرد که `formValid` و در صورت مصرف، `status` را در `buildWhen` مقایسه می‌کند. این builder می‌تواند در همین فایل و دور بخش دکمه بماند؛ ساخت ویجت، فایل یا State جدید برای یک دکمه لازم نیست.

به‌روزرسانی‌های اعتبار فرم در اکشن‌های فعلی باقی می‌مانند؛ محاسبه به UI یا سازندهٔ Cubit منتقل نمی‌شود و `emit` اولیهٔ حذف‌شده برنمی‌گردد.

### وضعیت loading در نمونهٔ فعلی

فیلد `status` از نوع `RequestStatus` هم‌اکنون در `AuthState` موجود است؛ اما `requestOtp()` فعلی یک عملیات هم‌زمان و آزمایشی است و درخواست شبکه ارسال نمی‌کند. این اکشن loading واقعی تولید نمی‌کند.

برای غیرفعال‌کردن فعلی دکمه، همان `formValid` کافی است. هنگام اتصال واقعی ارسال رمز، وضعیت loading پیش از `await` و موفقیت یا خطا پس از پاسخ ثبت می‌شود. نباید برای نمایش loading، تأخیر یا درخواست ساختگی اضافه شود. اگر ارسال OTP و تأیید ورود عملیات مستقل شوند، status مستقل برای هر عملیات باید در همان محدودهٔ اتصال سرویس تعریف شود.

### اعتبارسنجی در خود اکشن حفظ شود

`requestOtp()` باید همچنان اعتبارسنجی مرکزی خود را داشته باشد؛ callback صفحه‌کلید کپچا نیز آن را فراخوانی می‌کند. غیرفعال‌بودن دکمه جایگزین محافظ اکشن نیست. زمان اتصال سرویس، جلوگیری از ارسال تکراری و قفل متناسب با درخواست در حال اجرا هم در Cubit اعمال می‌شود.

## ۵. رفتار مورد انتظار

- در شروع، دکمه غیرفعال است؛ چون `formValid` پیش‌فرض false دارد.
- کد ملی نامعتبر یا ناقص، شماره موبایل نامعتبر یا ناقص، یا کپچای کمتر از ۶ رقم، دکمه را غیرفعال نگه می‌دارد.
- با معتبر شدن کد ملی و قالب موبایل و تکمیل ۶ رقم کپچا، دکمه فعال می‌شود.
- حذف یا نامعتبر کردن هر ورودی، دکمه را دوباره غیرفعال می‌کند.
- `refreshCaptcha()` اکنون کپچا را پاک و `formValid` را false می‌کند؛ با اتصال دکمه به State، دکمه نیز غیرفعال می‌شود.
- کپچای ۶ رقمی اشتباه هم ممکن است دکمه را فعال کند؛ رد پاسخ اشتباه وظیفهٔ سرویس کپچا است. مقایسه با عدد ثابتِ تصویر نمونه راهکار صحیح اتصال سرویس نیست.
- State اولیهٔ سفارشی، مانند داده‌های تست، باید مقدار سازگار `formValid` داشته باشد؛ سازنده آن را دوباره محاسبه نمی‌کند.

## ۶. تطبیق مستندات و بررسی‌های لازم هنگام پیاده‌سازی

[مستند ورود](../doc/login/development.md) رفتار قبلی دکمهٔ آبی و فعال در فرم خالی را ثبت کرده است. درخواست جدید صاحب پروژه، این رفتار را به غیرفعال بودن تا تکمیل ورودی‌های معتبر تغییر می‌دهد؛ هنگام پیاده‌سازی، توضیح مستند و تست‌های وابسته باید با رفتار جدید همگام شوند.

برای تغییر واقعی، بررسی‌های رفتاری زیر مناسب‌اند:

- فرم خالی، ناقص، کد ملی با checksum نادرست و موبایل با قالب نامعتبر: دکمه disabled.
- هر ترتیب ورود سه فیلد، از جمله ارقام فارسی: فعال‌شدن فقط پس از کامل‌شدن همهٔ شروط.
- پاک‌کردن فیلد یا refresh کپچا: برگشت به disabled.
- کنترل صحیح callback صفحه‌کلید در فرم نامعتبر.
- پکیج: `isActive: false` با callback غیر null، جلوگیری از کلیک، semantics غیرفعال، loading و سازگاری `onPressed: null`.
- پکیج: حذف آرگومان `isActive` در مصرف‌کنندگان قبلی همان رفتار پیشین را حفظ کند.

## تحویلی این مرحله

این مرحله فقط بررسی کد و ثبت پیشنهاد بود. هیچ فایل Dart در برنامه یا پکیج `avp_ui` تغییر نکرد و تست یا analyze جدید اجرا نشد. تصمیم پیشنهادی: استفاده از `formValid` موجود در برنامه و افزودن سازگار `isActive` در کنار `isLoading` موجود به دکمهٔ پکیج.
